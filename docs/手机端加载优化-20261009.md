# 手机端包材库加载优化

## 原因与实测基线

2026-10-08 在正式域名、正确 Host／SNI、严格 TLS 校验下测试；本机 DNS 不稳定时仅对诊断连接指定当前主机 47.79.233.3，不修改系统 DNS。业务端原启动下载 11,851 条活动记录：JSON 解压后 33,437,444 字节，gzip 传输 1,375,284 字节。本机请求约 3.48–3.62 秒，服务器单次序列化约 1.79–1.91 秒。手机还须解析完整目录和生成搜索索引。

客户首批 24 条安全记录的响应为 9,289 字节，gzip 2,806 字节，但每次都重新投影／核验目录。服务器约 0.35–0.50 秒，本机 HTTPS 约 1.25–1.46 秒。手机 136 像素宽的卡片下载 1,303–1,549 像素的图片；六张抽样员工图为 146–211 KB，客户图为 103–171 KB。图片 no-store 导致重复访问重传；五张手机轮播背景约 1.1–1.2 MB／张。懒加载已存在，本轮保留。

这些是本机与服务器测量，不是实际手机 4G／5G 的秒数承诺。

## 修改顺序与边界

1. 列表、对比和小图采用 512 像素缩略图；详情与下载保留大图。
2. 私有 ETag 条件缓存，权限先检查再返回 304，撤销批准和退出立即拒绝。
3. 员工／管理员在服务器搜索、归并系列后分页，复用与前端相同的查询规则，保留多选、编号、中英文、搜图、收藏、跨页对比、编辑和导出。
4. 客户手机公司图片和轮播使用轻图，PC 与完整查看维持原图。
5. 复用安全投影／员工查询索引，文件按块传输，GET／HEAD 持久连接，POST 提前拒绝后关闭连接。
6. 仅优化正式域名 Nginx 的 HTTP/2 和后端连接复用；不改变用户、密码、登录保护、域名或已批准的产品范围。

## 首页、海报与传输算法补充（2026-10-09，已上线）

用户复测慢点为“海报与首页”。再次诊断发现两类因素：电脑宽屏及放大仍下载 MB 级原图，证书列表也直接使用原 PNG；实际维护 TCP 连接存在重传，CUBIC 的 cwnd 缩至 2。服务器当时 load 约 0.03、可用内存约 2.4 GB，未观察到 CPU／内存饱和。该证据支持减少传输量和测试拥塞控制，不足以断定所有手机慢速均由同一网络原因造成。

### 已发布内容

- 35 张在用公司／证书／轮播／海报素材，生成 70 张带来源摘要的 512／1280 像素 WebP，原图与 PDF 不改写。手机首页用 512、宽屏用 1280；列表证书用 512。70 图总计 3,220,262 B，512 图最大 41,658 B、1280 图最大 158,196 B。
- 海报只有在产品页可见、进入海报滚动容器附近 120px 时才请求；首页和隐藏分类不触发请求。放大先显示小预览，再取 1280 图，迟到请求不能覆盖其他图或重开弹窗。完整原图下载保持。
- 正式构建将 CSS 内置、三段数据／控制脚本合为一个 defer 脚本；沿用 CSP、私有 ETag 和每次访问的登录／授权检查。首页、产品、联系仍独立分页。
- 正式主机 `47.79.233.3` 使用发行版已有内核 `6.6.102-5.3.1.alnx4.x86_64` 的 `tcp_bbr` 模块，默认拥塞控制从 cubic 改为 bbr。新 HTTPS 和 SSH 连接已实际使用 bbr；保留 fq_codel，不安装新内核、不重启服务。Linux 4.20+ 的 TCP pacing 不要求必须更换为 fq，依据 [Google BBR 官方说明](https://github.com/google/bbr/blob/master/Documentation/bbr-quick-start.md)。
- `/etc/modules-load.d/yuanze-bbr.conf` 与 `/etc/sysctl.d/99-yuanze-bbr.conf` 持久化；通过内核状态、文件内容及定向 `sysctl -p` 核验。这里的“开机配置完成”不表示已重启服务器验收。

# 当前包材库使用 Codex 与 Sites 的选择

核对日期：2026-09-29。用户已决定保留现有网站，Sites 若不能直接整理现有后端和数据库，则本轮不采用。

## 已确认的事实

- 当前包材库运行在阿里云，使用 Python、三个 SQLite 数据库、本地图片文件和 ONNX 搜图服务。
- 已通过 Sites 工具读取原工程登记的“源泽业务协同 · 参考系统”。该项目是早期虚构数据演示，目前没有部署版本、线上 URL 或 D1 数据库绑定；它不是当前正式包材库。
- Sites 支持创建、托管、继续修改兼容网站，提供结构化数据库 D1 和文件存储 R2。其数据库检查工具只读取所选 Sites 项目的数据库，不能拿阿里云 SQLite 路径来接管现有数据库。
- 现有 Python 常驻服务、systemd、磁盘访问及 ONNX 后台工作线程，无法原样作为当前 Sites 工作流要求的 Worker 部署产物。

## 三种方式的比较

| 方式 | 对当前工程怎么做 | 优点 | 工作量与限制 | 当前建议 |
| --- | --- | --- | --- | --- |
| 只用 Codex 开发维护，阿里云继续运行 | 在桌面 Git 工程改代码、测试、提交，再更新原服务器 | 现有账号、URL、权限、图片和搜图可以持续使用；能直接检查服务器与数据库 | 服务器、证书、备份和发布仍需维护 | **最适合当前阶段** |
| Codex + Sites | Codex 开发/测试一个兼容 Sites 的工程，再由 Sites 托管；或者另做独立的展示原型 | 开发工具与托管能力可以协作；适合重新设计后发布的兼容项目 | 结合使用不会免去适配。若前端放 Sites、后端留阿里云，会新增跨域会话、同源校验、接口和两套部署的维护 | 当前核心系统暂不引入；需要独立原型时再考虑 |
| 只通过 Sites 界面提出修改并托管 | 先迁移/重写为 Sites 兼容实现，再在 Sites 内持续修改 | 对新建展示站、表单和平台适配的内部工具，发布步骤较少 | 当前登录、原图访问、Excel 导入和搜图都需逐项重做/验证；不是把文件夹上传即完成 | 不建议用来直接替换现有包材库 |

“只使用 Sites”仍然涉及生成代码、数据模型、权限与测试。它可以成为日常修改入口，但不是独立于 AI 使用限制的免费维护服务。官方说明目前 Sites 为 beta，受套餐用量及运行能力限制；没有依据保证它会比当前方式消耗更少额度。

## 与本项目直接相关的迁移障碍

1. **登录方式**：现有员工用管理员分配的账号登录。Sites 的受限分享与 ChatGPT 登录、网站内角色权限是不同层次。不能假定原有账号自动迁移，也不能假定每位同事都已具备对应访问方式。
2. **图片保护**：原图可能带供应商/报价。现有客户端使用明确批准、每请求校验的图片与容量白名单，换托管平台必须保留同等隔离。
3. **数据库一致性**：编号不可变、版本冲突、审计、原始证据、历史快照和认证撤销都必须保留；D1 兼容 SQL 不等于当前 Python 数据访问代码可原样执行。
4. **搜图计算**：当前依赖 CPU 上的 ONNX 模型和持久索引，须继续留在外部受控服务，或另行改造后验证，不保证能直接运行在 Sites。
5. **同事实际访问**：现有站点受控于当前域名与服务器；更换平台必须用公司实际网络和手机验证，不能承诺仅迁移就消除网络故障。

## 本次决定

继续用 Codex 整理和维护现有后端、数据库；不将真实数据库、账号或公司素材上传到 Sites，不修改 Sites 分享范围，也不改当前网址。后端和数据库的整理成果见 `后端与数据库说明.md` 及只读检查工具。

参考：[OpenAI 官方 Sites 文档](https://learn.chatgpt.com/docs/sites)，以及本机 Sites 插件的运行、存储和认证规范。上述工作量判断结合当前项目源码得出，不代表所有网站都应采用同一种方案。

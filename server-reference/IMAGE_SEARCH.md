# 内部包材图片检索

本功能让已登录员工上传、拖放或粘贴一张包材图片，按视觉相似程度排列库内候选记录。多款产品同处一张图时，可在上传窗口框选其中一款。搜图后仍可组合文字、类型、材质、容量和报价资料筛选；“清除搜图”恢复普通检索。

## 当前检索范围

当前发布为 `20260927-materials-v1`，线上核验索引包含 **3,175 张图片、3,186 条记录**，状态为 ready，待处理与失败图片均为 0。此前 `20260924-admin-v1` 已验证索引为 310 张图片、319 条包材记录。

初始图库来自 `private/catalog.json` 和 `private/media/`，本次增量底稿为 `private/materials-20260924.json`；在线图库以后台持久化记录和图片关联为准。本次纳入 `kind=package` 的合格产品图，以及 `kind=source_page` 的图册原页／表格图片线索；合格图片角色为供应商图、产品图、询价参考图。缺失图片、归属待核对图片和参考角色图片不参与排名；`process_rule` 不作为产品搜图候选。

新增资料来自 21 份 PDF 和 4 份 Excel。2,608 张 PDF 原页与 259 条表格图片卡片合计 2,867 条 `source_page`，单独标注为原页／图片线索。**没有声称已自动抠出或逐一识别画册中的每个单品**：页面图可能包含多款、不同容量或套装，索引的是整张来源图。搜到原页后，业务员可查看原图，并打开该页已关联的产品记录核对型号、规格及出处。

本次线上核验全库为 11,006 条记录，其中 8,001 条是产品来源条目，包含 OCR 待核对条目；另外有 91 条独立工艺与价格参考、47 条原有其他资料。并非每个产品来源条目都有可独立检索的单品图片，不能将产品记录总数当作搜图覆盖数。多条记录也可能共用同一张图，图片数、记录数与去重款式数是不同口径。

界面展示的实际覆盖数量来自 `/api/image-search/status`。本次上线核验结果记录在 `work/site-materials-20260924/live-verification.json`，实际原图查询的对应来源进入前 3 名。该单次核验不代表通用检索准确率；后续索引若仍在构建，只能说明已完成部分可检索。

## 排序方法与使用边界

本地 DINOv2-small 量化 ONNX 模型分别提取灰度图与彩色图的特征。图片经 EXIF 方向纠正、透明背景铺白、等比例缩放及白边填充后进入模型，避免直接中心裁剪截掉高瓶或泵头。

当前相似分数为 `0.8 × 灰度特征余弦相似度 + 0.2 × RGB 特征余弦相似度`。同一记录关联多张图片时取最高分，并展示该次匹配到的图片。这是为“瓶型与结构优先、颜色印刷次之”设置的启发式方案；灰度特征并非纯形状特征，背景、印刷、拍摄角度、成组陈列仍会影响排名。

分数不是准确率或同款概率；系统尚未用本公司标注样本校准准确率。相似外观不证明容量、材质、口径、泵盖兼容性或料体适配一致，也不保证找出所有相似款。业务员需要核对原始规格和实物；原页相似尤其不能直接当作页内某一款产品的相似度。缺失参数保持空白，不从原图或相邻款式推断价格。印刷工艺标准和历史参考规则单独保留，系统不自动录入或计算逐款工艺价格，也不会通过图片自动调整 MOQ、货期或报价。

## 登录与图片处理

- 状态接口和查询接口均要求现有内部登录会话。POST 查询还检查 Origin 和 CSRF，验证成功后才读取上传内容。
- 查询图片从浏览器发往公司自己的 HTTPS 网站，在服务进程内解码和推理；不保存查询图片、查询向量或查询历史，不调用外部图片识别服务。前端预览保留在当前页面内存中，清除搜图或离开页面后不作为历史查询保存。
- 应用请求日志不记录请求体、Cookie、凭据或查询字符串。ONNX Runtime 遥测事件已显式关闭。模型文件预先下载后，运行时检索和索引重建均不需要外网。
- 员工使用员工账号查询，独立管理员通过 `/admin` 维护图库；账号角色与停用状态由服务端检查。该接口及原始供应商图片不是客户公开展示接口。管理员上传产品图片会持久保存，和不落盘的员工搜图查询是不同用途。

## 上传限制与资源控制

浏览器可选择 JPEG、PNG、WebP，原文件上限 **10 MiB**、最长边 16,000 像素、总计 4,000 万像素；读取后先在浏览器缩小到最长边 **1,280 像素**，用户可再框选，最终以 JPEG 提交。

后台独立验证真实图片格式，不只相信文件后缀或 MIME。实际提交的编码图片须不超过 **6 MiB**、总计 **400 万像素**、最长边 10,000 像素，且每边至少 16 像素；多帧文件被拒绝。Base64 JSON 请求体另有对应长度上限。前端原图 10 MiB 与后端提交图 6 MiB 是不同阶段的限制。

后台在读取和解码查询前取得单任务锁，同一时刻只处理一张查询图；繁忙时直接返回 429，不积压解码任务。模型仅用 CPU，推理线程数设为 1。浏览器取消操作会丢弃对应结果，但已开始的服务端推理可能继续完成。较大的离线原图使用独立上限：32 MiB、2,000 万像素；该上限不开放给查询上传。

| --- | --- |
| NumPy | 2.2.6 |
| Pillow | 12.3.0 |
| ONNX Runtime | 1.30.0 |

模型原始来源为 [Meta / facebook 的 DINOv2-small](https://huggingface.co/facebook/dinov2-small)，ONNX 量化文件来自 [Xenova/dinov2-small](https://huggingface.co/Xenova/dinov2-small/tree/c2bb04a51fab207c420665f1946016107bffc701)。当前固定 revision 是 `c2bb04a51fab207c420665f1946016107bffc701`，远端 `onnx/model_quantized.onnx` 在本地命名为 `model.onnx`，未重新训练或修改权重。模型 SHA-256 为：

`3afdc8bc63b50558d6e5770f5b799bb82455c2311183a2de43803f343a29d917`

`private/image-search/model/model-source.json` 保存了模型、配置、预处理配置的固定下载 URL、长度与 SHA-256。恢复模型时使用该清单中的固定 URL 并逐项核对 SHA-256；不要用浮动的 `main` 替换当前文件而沿用旧索引。附带的 `LICENSE` 是 [facebookresearch/dinov2 官方 Apache 2.0 许可文本](https://raw.githubusercontent.com/facebookresearch/dinov2/main/LICENSE)，`NOTICE` 记录模型来源及本项目使用方式。

## 安装与重建

在待发布版本的 `server-reference` 目录中，用与服务相同的 Python 环境执行。`python3` 在下面表示该环境的解释器，不应另选一个缺少依赖的系统解释器。

```sh
python3 -m pip install -r requirements-image-search.txt
python3 build_image_index.py --private ./private
python3 -m unittest test_server test_http test_image_search
```

上述脚本维护 release 内的初始基线索引；确保 `private/catalog.json`、`private/media/` 和 `private/image-search/model/` 已完整就位后，在待发布目录完成构建与验证。它不代替后台资料的动态索引，不应使用旧原始目录覆盖管理员维护后的产品。

`20260924-admin-v1` 起使用 `ManagedImageSearch` 管理在线图库；`20260927-materials-v1` 扩展原页线索的检索范围。产品、图片、归档及恢复操作会触发后台更新；持久化动态索引位于 `YZ_STATE/image-search/`，上传图片位于 `YZ_STATE/uploads/`，实际记录来自 `catalog.sqlite`。管理员可在产品列表底部查看进度，或点击“更新搜图索引”重试。索引更新完成后在线生效，不需要为了每次内容编辑重启服务。状态目录和 release 分开保存，升级代码不能覆盖动态索引或上传文件。

模型与预处理变更仍需在维护中核对指纹并重新构建，不能沿用不匹配的向量。不要在同一目录并发运行多个独立重建进程。当前服务虚拟环境为 `/opt/yuanze-reference/venvs/admin-20260924`。

当目录、图片、模型、预处理方案或灰度权重变更时，必须重建索引。构建过程结束前会重新核对来源，发现构建期间资料变更即停止。发布与重启步骤以部署文档和实际服务环境为准。

## 索引失效与降级

服务启动时检查目录及图片哈希、模型及预处理指纹、数组文件哈希、记录映射、向量维度与归一化情况。缺少依赖、模型或索引，索引损坏、过期或映射不一致，都会使图片检索停用，并向界面返回“索引暂不可用”。登录、普通目录、文字和分类检索继续可用。

先修复来源或依赖；在线产品与图片关联问题可在后台修订并重新更新索引，服务依赖或模型变更需按发布流程重建并重启。不要删掉哈希或映射检查来强行开启旧索引。`ImageSearchService.failure_reason` 可在本地维护排查时查看；内部路径和错误细节不会通过状态 API 暴露给用户。
